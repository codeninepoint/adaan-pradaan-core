RBAC & Relationships — Overview
The platform uses role-based access control (RBAC), not relationship-based access control (ReBAC). Authorization is a role lookup per tenant, not a graph walk — the "relationships" here are the organization/tenant/membership hierarchy that roles are bound within.
ℹ️ A note on terminology: this system has no ReBAC engine (no relationship graph, no "user → owns → document → shared-with → team" style checks). Every authorization decision is: does this principal have an active role binding with the needed permission, in the tenant named by X-Tenant-Id? The Entity Relationships page visualizes the ownership/membership structure those bindings live inside — that's the closest concept to "ReBAC" this system has.

🏷️ Two separate role ideas — don't confuse them
tenant.org_memberships.role Governance of the organization — owner or member. Controls org/vendor actions. Not an RBAC grant.
authz.roles + authz.principal_roles The actual permission bundle checked on API calls. Never stored in the JWT — looked up fresh per request.
🔐 How a request gets authorized

The access token carries only sub, uid, pid, and expiry — never roles. Each protected call reads X-Tenant-Id, looks up authz.principal_roles for that principal in that tenant, and checks for an active binding with the required permission. Tenant-scoped roles never receive platform.* permissions, and platform-scoped roles never receive tenant permissions — the two catalogs don't mix.

Service Account Roles
A service account is a machine principal in one tenant — no email, no Keycloak login, no org or tenant membership row. It gets RBAC roles exactly like a user.

🔐 Rules enforced
  • List, create, assign role, rotate, and revoke all require tenant.admin in that tenant — same permission, not a separate "service account admin" code.
  • One active key at a time. Rotate revokes the old key and issues a new one atomically; revoke alone leaves no replacement.
  • A second active binding of the same role on one service account is 409.
  • The raw API key is shown once at creation/rotation. Only a hash and an ak_ + 8-hex prefix are stored after that.
  • The API key itself is never accepted as a Bearer token for the management APIs — those still require a user's access token.

🚧 Not a real entity yet

"Workspace" is not a lifecycle object. Signup names the org "{display name} workspace" as a label, and a resource may be created with resource_type = workspace — but there is no workspace status, no workspace table, and no workspace API. Don't model it as a node with its own state.

Platform Operators
Organizations whose members may review vendor applications. Not an RBAC role — a flag on the organization itself.
ℹ️ is_platform_operator is set the moment a signed-in user calls GET /auth/me if their email is in TENANT_PLATFORM_OPERATOR_EMAILS and they are an owner of that organization. There's no admin toggle for this in the product today — it's config-driven.

✅ What the flag actually unlocks

Vendor approve and reject check this flag directly — not an RBAC permission code. A user needs active membership in a is_platform_operator = true org; nothing else grants access to /app/vendor's review queue. The platform-scoped platform-admin / platform-support roles exist in the catalog but aren't what this screen checks.
